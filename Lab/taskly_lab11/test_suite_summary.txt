5. KNOWN LIMITATIONS
══════════════════════════════════════════════════════

1. In-memory only: TaskRepository does not persist data.
   Tests reset state between runs via setUp(). A real app
   would need database or shared-preferences persistence
   tests.

2. No state-management tests: The app uses direct setState()
   without a state management solution (e.g. Riverpod,
   BLoC). As the app grows, this limits testability.

3. Widget test coverage of animations: AnimatedContainer
   transitions are not fully observable in widget tests
   because pumpAndSettle() resolves them. Visual regression
   tests (e.g. golden tests) would be needed.

4. No golden/screenshot tests: Pixel-perfect rendering is
   not covered. Flutter's matchesGoldenFile() could be added.

5. Integration vs true E2E: The "integration" tests here are
   widget-level tests (not flutter_driver or integration_test
   package tests). True device integration tests would run on
   a physical device/emulator via `flutter test integration_test/`.

6. Task ID collision: IDs are generated from microsecond
   timestamps. Under rapid parallel inserts (unlikely in a
   mobile app), collisions are theoretically possible.
